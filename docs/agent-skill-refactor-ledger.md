# Agent Skill Refactor Ledger

## Task contract

- **Requested outcome**: Refactor orchestrator agent prompts, packaged skills, metadata, and runtime wiring so prompts keep compact core contracts while long or conditional procedures move into valid skills without weakening behavior.
- **Constraints that must stay true**:
  - hard safety, ownership, machine-output, permission, and status-transition rules must remain enforceable;
  - `master` is the authoritative baseline;
  - runtime exposure must not claim a stronger isolation model than the code actually enforces;
  - no normative rule may disappear without explicit accounting.
- **Facts gathered before editing**:
  - prompts are loaded from `agents/*.md` in `src/index.ts`;
  - agent metadata lives in `src/orchestrator-agents.ts`;
  - static install-time config changes are the realistic place to register packaged skill paths;
  - runtime can narrow `tools.skill` and `permission.skill` per agent;
  - public OpenCode docs describe `permission.skill` and `tools.skill`, and public issue `anomalyco/opencode#20940` shows plugin `config()`-time `skills.paths` mutation is too late for skill discovery.
- **Surfaces to change or check**:
  - `src/index.ts`
  - `src/orchestrator-agents.ts`
  - `src/orchestrator-install.ts`
  - `src/orchestrator-prompts.ts`
  - `agents/*.md`
  - `skills/**/SKILL.md`
  - `package.json`
  - tests and role/docs surfaces
- **Checks required before done**:
  - formatting
  - lint
  - TypeScript build
  - test suite
  - rule-ledger recheck with explicit final status per entry

## Stage 1 summary before edits

### Core-prompt rules that must remain

- safety and permission boundaries
- ownership of state files and canonical structures
- machine-readable output contracts
- blocker semantics and completion/readiness gates
- command-policy discipline
- status-transition correctness
- agent-boundary clarity

### Good candidates for skill extraction

- Planner gate-cycle and proposal triage procedure
- Refiner requirement-to-evidence and command-definition procedure
- Spec-Checker operational consistency checks
- Todo-Writer decomposition and remediation procedure
- Executor working loop, delegation, and completion-review procedure

### Duplicate or obsolete material to remove safely

- repeated explanatory prose that restates a stricter still-live rule
- examples that duplicate a preserved machine-readable contract
- half-old source/docs wording that already assumes skills without matching runtime wiring

### Runtime exposure that appears technically feasible

- install-time registration of packaged `skills/` path
- per-agent `tools.skill` enable/disable
- per-agent and global `permission.skill` allow/deny rules
- static per-agent allowlists as the strongest practical fallback when dynamic session-level isolation is unavailable

## Public-source notes that constrain the design

- OpenCode docs describe `permission.skill` and `tools.skill` as the supported control points for skill visibility and access.
- OpenCode docs also describe default skill discovery locations, while public upstream source shows support for static `skills.paths`.
- Public upstream issue `anomalyco/opencode#20940` reports that plugin `config()`-time mutations to `skills.paths` are invisible to skill discovery, so packaged skill directories must be registered through static config written at install time rather than through runtime plugin mutation.
