# ADR-006: Orchestrator CLI の UX 改善とローカライズ / 補完

- **日付**: 2026-04-03
- **ステータス**: Proposed
- **関連ファイル**:
  - `src/cli.ts`
  - `src/cli-args.ts`
  - `src/orchestrator-status.ts` (新規想定)
  - `src/orchestrator-doctor.ts` (新規想定)
  - `src/orchestrator-fix.ts` (新規想定)
  - `README.md`

## 文脈（Context）

OpenCode Orchestrator の CLI は現在、次のような特性を持っている。

- コマンド名は `opencode-orchestrator` のみで、短いエイリアスがない。
- 主なサブコマンドは `list` / `loop` / `clear` / `exec` / `install`。
- 長期タスクの状態は、計画フェーズと実行フェーズで複数ファイル
  (`acceptance-index.json`, `spec.md`, `command-policy.json`, `status.json`,
  `proposals.json`, `todo.json`) に分割して保存される。
- 計画フェーズは OpenCode TUI 上の Orch-Planner から行い、CLI 側は
  `loop --task <task>` をエントリポイントとする。

一方で、利用者視点では次のような UX 上の問題が指摘されている。

1. **導入と異常系の扱いが弱い**
   - Node.js / npm / npx / `opencode` コマンドの有無やバージョンを簡単に
     確認する手段がない。
   - ネットワークや state ディレクトリなど、環境側の前提条件が揃っているかを
     一括で診断するコマンドがない。
   - README は存在するが、実際の診断フローを CLI が肩代わりしておらず、
     導入や失敗時の切り分けが人手作業になりやすい。

2. **計画フェーズの可視性が弱い**
   - Orch-Planner の説明文に内部識別子が多く含まれ、人間向けの整理として
     十分とは言えない箇所がある。
   - 計画フェーズの成果物（受け入れ条件や `spec.md` の内容）を CLI 経由で
     概観する手段が弱く、最終的にはファイルを直接読む必要がある。

3. **実行フェーズの入口が扱いづらい**
   - `npx opencode-orchestrator loop --task my-task-with-description` のように、
     コマンドが長くなりがちで、タスク名の補完や再開がしづらい。
   - 問題が起きたとき、「まず何を見るか」「次にどのコマンドを打つか」が
     CLI からは分かりづらい。

4. **補完とローカライズが不足している**
   - 公式な引数補完がなく、サブコマンド名や `--task` の候補がタブ補完で
     出ない。
   - CLI のメッセージは主に日本語だが、言語切り替えの仕組みがなく、
     英語環境や Windows 環境での体験が不均一である。
   - 人間が読むメッセージの中に `command-policy.json` や `loop_status` など、
     内部実装向けの用語がそのまま露出しやすい。

これらは、内部状態や制御ロジックが厳密である一方、CLI が
「導入」「診断」「復旧」「日常運用の入口」を十分に肩代わりできていない、
という問題として整理できる。

## 決定事項（Decision）

この ADR では、Orchestrator CLI の UX を次の方針で再設計する。

1. **短いエイリアス `ococ` を追加する。**
   - `ococ` を `opencode-orchestrator` と等価な CLI エントリポイントとして
     追加する。
   - ドキュメントやヘルプでは長い名前・短い名前の両方を案内するが、
     日常利用の例では `ococ` を中心に示す。

2. **日常運用向けの高レベルサブコマンドを追加する。**

   低レベルな `loop` / `clear` / `exec` / `install` に加えて、
   次の高レベルサブコマンドを追加する。
   - `status`: タスク 1 件の状態を人間向けに要約する。
   - `doctor`: 環境全体（Node.js / npm / npx / `opencode` / state ディレクトリ /
     ネットワークなど）を診断する。
   - `fix`: 特定タスクに紐づいた問題（計画不足、必要なコマンドの不足、
     未処理の提案など）を診断する。
   - `run`: 実行可能であれば実行ループを開始し、準備が足りない場合は
     理由と次の操作を示す高レベル入口とする。
   - `resume`: 直近のセッションやタスクから実行を再開する入口とする。
   - `completion`: 各シェル向けの補完スクリプトを出力する。
   - `__complete`: 補完スクリプトから呼び出される、補完専用の非公開サブコマンドとする。

   `loop` / `clear` / `exec` / `install` は引き続き提供するが、
   「細かく制御したい場合の低レベル API」として位置づける。

3. **タスク名の自動解決と「もしかして」候補を導入する。**
   - `run` / `resume` / `status` / `fix` では、`--task` / `-t` を省略した場合に
     作業ディレクトリと過去の利用履歴からタスク名を自動決定する。
   - 指定されたタスク名が存在しない場合や、自動決定に失敗した場合は、
     利用可能なタスクの一覧を必ず表示する。
   - 入力値に近いタスク名があれば、`"もしかして: ..."` / `"Did you mean ...?"`
     の形式で候補を提案する。
   - これらのメッセージでは内部ファイル名や内部ステータス値を出さず、
     「なぜ使えないのか」「何を指定すればよいか」を平易な文章で説明する。

4. **すべてのメッセージに対して、日本語と英語の両方を用意する。**
   - CLI が人間に向けて表示するメッセージはすべて、英語版と日本語版の
     両方を用意する。
   - 既定の表示言語は次のルールで決める。
     - Windows 環境では、Windows のロケール設定を優先する。
     - それ以外の環境では、`LC_ALL` → `LANG` の順に環境変数を参照し、
       `ja` 系であれば日本語、それ以外は英語とする。
     - ロケールが取得できない、もしくは未対応の言語の場合は英語に
       フォールバックする。

5. **人間向けメッセージに内部実装の用語を出さないガイドラインを設ける。**
   - CLI が標準出力・標準エラーに表示するメッセージでは、
     `command-policy.json`, `status.json`, `proposals.json`, `loop_status`,
     `needs_refinement`, `blocked_by_environment` などの内部名称をそのまま
     見せない。
   - これらが原因であっても、説明は「計画が足りない」「開発環境の制約で
     止まっている」など、利用者視点の自然な文章に言い換える。
   - 開発者向けの README や ADR では内部名称をそのまま用いてよいが、
     CLI のメッセージとは切り離して扱う。

6. **メッセージカタログ（i18n）を導入する。**
   - すべての人間向けメッセージに一意のキー
     （例: `error.task_not_found`, `hint.did_you_mean`, `status.summary`）を付与する。
   - CLI コード側ではメッセージキーとプレースホルダ
     （`{task}`, `{candidates}` など）のみを参照する。
   - 実際の文言は、言語ごとのマップから取得し、英語版・日本語版の双方を
     管理する。

7. **補完ロジックは `__complete` に集約し、`completion` と各シェルは薄いアダプタにする。**
   - `__complete` は、現在のコマンドラインとカーソル位置を受け取り、
     候補の種別・値・説明を機械可読な形式で返す隠しサブコマンドとする。
   - `completion` は、指定されたシェル（bash / PowerShell）向けの補完スクリプトを
     出力し、そのスクリプト内から `__complete` を呼び出す。
   - 補完候補としては、サブコマンド名・オプション名・タスク名・提案 ID などを
     含め、タスク名については現在の作業ディレクトリと最近の利用状況を
     もとに優先度を付ける。

8. **`doctor` と `fix` の責務を分離する。**
   - `doctor` は環境全体の診断専用とし、Node.js / npm / npx / `opencode`
     コマンドの存在、state ディレクトリの書き込み可否、ネットワーク疎通などを
     チェックする。
   - `fix` はタスク固有の診断専用とし、計画ファイルやタスク状態、
     未処理の提案、必要なコマンドの不足などを読み取り、「何が原因で止まっているか」
     と「次に何をするとよいか」を人間向けにまとめる。
   - どちらのコマンドも read-only とし、ファイルの自動修正や提案の解消は行わない。

## 詳細設計（Details）

### 1. CLI 全体像

この ADR 適用後に想定される CLI の表面 API は次の通り。

- 高レベル入口（ふだん使い向け）
  - `ococ run [--task/-t <name>] [options] [prompt]`
  - `ococ resume [--task/-t <name>] [options]`
  - `ococ status [--task/-t <name>] [--json] [--verbose]`
  - `ococ doctor [--json] [--no-network]`
  - `ococ fix --task/-t <name> [--json] [--verbose]`
  - `ococ completion <shell>`

- 低レベル / 既存 API
  - `opencode-orchestrator loop --task <name> [...]`
  - `opencode-orchestrator list [...]`
  - `opencode-orchestrator clear --task <name> [...]`
  - `opencode-orchestrator exec [...]`
  - `opencode-orchestrator install [...]`
  - `opencode-orchestrator __complete --shell <name> --line ... --cursor ...`

`opencode-orchestrator` でも同じサブコマンドを利用できるが、
日常利用の例では `ococ` を優先的に案内する。

### 2. タスク名の自動解決と「もしかして」候補

対象サブコマンド: `run`, `resume`, `status`, `fix`

1. `--task` / `-t` が指定されている場合
   - 指定された名前と完全一致するタスクが存在するかを確認する。
   - 見つからない場合は次のように振る舞う:
     - 利用可能なタスク名一覧を必ず表示する。
     - 編集距離や前方一致などで近い候補を探し、1〜数件を
       `"もしかして: ..." / "Did you mean ...?"` の形式で表示する。
     - メッセージ文面では内部ファイル名や内部ステータス値を出さず、
       「指定した名前のタスクは存在しない」「この中から選んでほしい」と
       いった平易な説明に留める。

2. `--task` / `-t` を省略した場合
   - 現在の作業ディレクトリに紐づく「直近のタスク」が記録されていればそれを採用する。
   - 記録がなければ、state ディレクトリ内のタスク一覧を取得する。
     - 1 件だけ存在する場合はそのタスクを自動採用する。
     - 複数ある場合は自動決定せず、一覧を表示してエラーとする。
   - この場合も、「どのタスクを使うかを指定してください」といった自然文のみを
     表示し、内部のファイル構造には触れない。

### 3. ローカライズ方針

- CLI の人間向けメッセージはすべて、メッセージキーを通じて管理する。
- 各メッセージキーに対して、英語版・日本語版の両方の文言を用意する。
- 表示言語は次の優先順で決定する。
  1. Windows 環境では、Windows のロケール情報（ユーザーの表示言語）を参照する。
  2. それ以外の環境では、`LC_ALL` → `LANG` の順で環境変数を参照する。
  3. 値が `ja` 系であれば日本語、それ以外は英語とする。
  4. どの情報も得られない、または未対応の言語の場合は英語にフォールバックする。
- テストでは、言語を明示的に固定したうえで期待する文言が出ることを確認する。

### 4. 人間向けメッセージのガイドライン

- CLI の出力には、次のような内部実装の用語を含めない。
  - ファイル名: `command-policy.json`, `status.json`, `proposals.json` など
  - 内部の列挙値: `loop_status`, `needs_refinement`, `blocked_by_environment`,
    `env_blocked` など
- 原因がこれらであっても、説明は利用者の観点から書き直す。
  - 例: 「このタスクはまだ実行を始められません。計画の見直しが必要です。」
  - 例: 「必要なコマンドが見つからないか、実行が許可されていないため、
    このタスクは開発環境の制約で止まっています。」
- 開発者向けの資料（README や ADR）では内部の用語・ファイル名を
  正確に記載してよいが、それらは CLI のメッセージに直接反映しない。

### 5. `status` コマンドの挙動（概要）

目的: タスク 1 件の「現在地」と「次に何をすべきか」を、人間に分かりやすい
形で表示する。

- 入力例:
  - `status --task/-t <name> [--json] [--verbose]`
- 内部で参照する情報:
  - タスク用の state ディレクトリ
  - 計画フェーズの成果物（受け入れ条件・仕様）
  - 実行フェーズの進捗を記録した状態
  - 提案の一覧
- テキストモードの出力要素:
  - タスクの短い説明（計画から取得した要約）。
  - 「計画中」「実行中」「完了」といった大まかな段階。
  - 直近の代表的な失敗理由（あれば）。
  - 開いている提案の数。
  - 必要であれば、直近セッションやステップの簡単な説明。
  - 「次にやるとよい操作」と、その例となるコマンド 1 行。
- JSON モードでは、同じ情報を機械可読な形で返す。

### 6. `doctor` と `fix` の役割

- `doctor`:
  - 環境全体の診断に特化する。
  - Node.js / npm / npx / `opencode` コマンドの存在、state ディレクトリの
    作成・書き込み可否、ネットワーク疎通などをチェックする。
  - メッセージは「何が不足しているか」「どう直すか」を中心に、
    平易な日本語・英語で提示する。

- `fix`:
  - タスク 1 件に絞って原因を調べる。
  - 計画ファイルの有無、実行を始める条件が整っているか、
    過去の実行で出た提案が残っていないか、監査で未達要件が残っていないか、
    すでに完了済みかなどを確認する。
  - 「このタスクはなぜ止まっているか」「次にどの操作を行うとよいか」を
    自然な文章でまとめる。
  - 代表例として、次のような状況を人間向けに説明する:
    - まだ実行を始められない（計画が足りない）。
    - 開発環境の制約で止まっている（必要なコマンドが見つからない / 許可されていない）。
    - 未処理の提案が残っている。
    - 直近の監査で要件未達が残っている。
    - すでに最終監査まで完了している。

どちらのコマンドも、状態を読み取って説明するだけであり、
自動的にファイルを編集したり提案を解消したりはしない。

### 7. `run` / `resume` の挙動（概要）

- `run`:
  - 実行に必要な条件が揃っていれば、内部的に実行ループを開始する。
  - 条件が整っていない場合は、どの条件が不足しているかを説明し、
    `status` / `doctor` / `fix` などのどれに進むべきかを示す。
  - 危険なオプションは露出させず、安全なオプションのみを受け付ける。

- `resume`:
  - 直近のセッションやタスクを特定し、その続きから実行を再開する。
  - すでに完了しているタスクや、計画が不十分なタスクについては再開せず、
    理由と次に行うべき操作を説明する。

`run` / `resume` いずれも、内部のファイル構造やステータス値を見せず、
「いまの状態」と「次の一手」だけを平易な言葉で表現する。

### 8. 補完アーキテクチャ（`__complete` / `completion`）

- `__complete`:
  - 入力として `--shell`, `--line`, `--cursor` などを受け取る。
  - 出力として、候補の種別・値・説明からなる行の集合を標準出力に返す。
  - 候補の種別には `subcommand`, `option`, `task`, `proposal` などを用いる
    （内部向けの値のため英語のままでよい）。

- `completion`:
  - `completion bash` は bash 用の補完関数を出力し、その中から `__complete` を
    呼び出す。
  - `completion powershell` は PowerShell 用の補完スクリプトを出力し、
    `Register-ArgumentCompleter` を使って `opencode-orchestrator` / `ococ` に
    紐づける。
  - 利用者は `.bashrc` や `$PROFILE` に 1 行追記するだけで補完を有効化できる。

- `install` との連携:
  - 可能であれば、現在のシェルを推測し、補完スクリプトの導入手順を
    `install` コマンドの出力に含める。
  - 自動で設定ファイルに追記する場合は明示的なオプションを要求し、
    失敗時は警告メッセージのみを出して終了コードはエラーにしない。

## 影響（Consequences）

### 利点

- 日常利用では `ococ run`, `ococ resume`, `ococ status`, `ococ doctor`,
  `ococ fix` だけで「実行の開始・再開・確認・診断」の流れがほぼ完結する。
- 問題が起きたとき、「まず何を見るか」「次に何をするか」が
  `doctor` / `fix` / `status` を通じて分かりやすくなる。
- CLI のメッセージが英語・日本語の両方に対応し、環境ロケールに応じて
  自然な言語を選べる。
- 人間向けメッセージから内部用語を排除できるため、内部構造を知らない
  利用者にも理解しやすい。
- 補完ロジックを `__complete` に集約することで、bash / PowerShell など
  複数シェルに対して一貫した体験を提供しつつ、保守コストを抑えられる。

### コスト・懸念点

- メッセージカタログとロケール判定ロジックの導入により、CLI コードの
  複雑さが増す。
- 既存のメッセージをすべて洗い出し、英語・日本語の両方を整える作業が
  必要になる。
- `status` / `doctor` / `fix` / `run` / `resume` / `completion` / `__complete` など、
  追加サブコマンドのテスト範囲が広くなる。

## 未解決事項（Open Questions）

- zsh や fish など、他のシェル向け補完をどこまで正式サポートするかは
  本 ADR では決めない。初期実装では bash / PowerShell のみを対象とし、
  必要に応じて別 ADR で拡張を検討する。
- Windows 環境でのロケール取得の具体的な実装方法
  （PowerShell 経由で取得するか、Node.js から直接取得するか）は、
  実装時に OS ごとの挙動を確認しながら決定する。
- タスク名の自動解決に利用する「最近のタスク」の記録形式と保存場所は、
  本体コード側での実装時に確定させる必要がある。
